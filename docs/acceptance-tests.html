00 Scope & conventions

The baseline bda61dc is the last commit before the sales pipeline work began. Everything below is new since then: five pipeline modules, access control, document printing, and the fixes found auditing them.

Outcome tags

Every scenario is tagged by what a pass looks like, because roughly a third of these tests pass by being refused. A rejection is the feature working.

  • Accept the action succeeds and state changes as described.
  • Refuse the action is rejected with a specific message. The test fails if it succeeds or if it fails with a different message.
  • Absent the control is not offered at all — no button, no menu item.

03 Proposals & BoQ

Pricing model decides how the total is built, and it is not cosmetic: model A ignores line items entirely, the others multiply them. WIN is a one-way door.

How each pricing model computes the total

ModelInput the form collectsTotal
AOne lump-sum figure, no line itemsThe figure as entered
BLine items with qty and selling priceΣ (qty × price)
C DLine items with up to four titled multipliersΣ (price × each non-zero title value)

Invoice amount is then items + management fee + VAT, where the fee is either a percentage of items or a flat figure, and VAT is skipped entirely for a No Tax invoice.

05 Receive Vouchers

An RV is an accounting document, not a discount. It reduces an invoice through five separate fields, and every one of them counts against the outstanding balance.

The arithmetic each test asserts

invoiceAmount = totalAmount + managementFee + VAT      (VAT = 0 when NO_TAX)

balanceDue    = max(0, invoiceAmount
                       − amountApplied
                       − ppnWapuDeduction
                       − pph23Deduction
                       − bankCharge
                       − othersAdjustment)

paymentStatus = FULLY_PAID   when balanceDue ≤ 0 and invoiceAmount > 0
                PARTLY_PAID  when any amount has been applied
                UNPAID       otherwise

Step 4Reconciledbalance and status recomputed

One gap worth knowing

Text fields are checked for emptiness, not for content: refDocNo accepts a single space, because the rule is @IsNotEmpty() on the server and min(1) in the form, and a space satisfies both. 11 The e2e suite

The suite exists. It lives in frontend/e2e/, runs on Playwright, and its test titles are the IDs in this document, so a failure names the scenario you are reading.

Running it

cd frontend
pnpm install
npx playwright install chromium     # once

pnpm e2e                  # everything
pnpm e2e:ui               # pick and watch tests interactively
pnpm e2e --grep VAL       # just the validation scenarios
pnpm e2e --project=viewer # what a read-only role is not offered

It expects the API on 127.0.0.1:3000 (the literal address, not localhost — that resolves to ::1 first on Windows and the API binds IPv4 only) and the UI on :5173, against a seeded local database. The config starts the Vite dev server for you and reuses one that is already up; it deliberately does not start the API, which needs its own database and is a step you take rather than a side effect of a test run. Never point it at production — it creates and deletes records and toggles the non-VAT settlement flag on a real internal account. Api.signIn() refuses any non-localhost API host unless E2E_ALLOW_REMOTE_API=1 is set, so one typo is not enough to reach live data.

Two decisions worth understanding before extending it

Preconditions go through the API, assertions go through the browser. Driving the UI to build a WIN proposal before every invoice test makes each test a dozen steps long and fail for reasons unrelated to what it checks. support/api.ts carries the factories — wonProposal(), createFitInvoice(), createProposalInvoice(). The deliberate exception is flows.spec.ts, whose whole point is that a person can complete the journey by hand.

Refusals are asserted on the server's own wording. A test that succeeds where a refusal was expected has found a bug; one that fails with a different message has found a changed rule. Both matter, so neither is matched loosely.

There are no test ids, and that is the suite's weak point

The frontend carries zero data-testid attributes and two aria-labels, so every selector comes from visible text or an ARIA role. Fine for headings and primary buttons; fragile for row menus, where every row renders an identical unlabelled trigger.

support/ui.ts works around it with row(), openRowMenu() and rowAction(), which reach a row by its document code before acting inside it — an unscoped click lands on whichever row the DOM happens to order first. Adding data-testid to the row trigger, the row keyed by code, and the dialog submit buttons would remove most of the remaining brittleness.

Traps that are already handled, and one that is not

  • Amounts render Indonesian — 52.000.000,00. The config pins id-ID so a runner in another region does not fail on separators, and parseIdr() converts a cell back to a number.
  • Codes carry a random segment, so rows are matched on the code captured from the create response. Nothing indexes rows by position.
  • Deactivating an account while its token is live needs two sessions; guards.spec.ts opens a second request context for it.
  • Several specs mutate shared state — an invoice balance, the one active print template — so fullyParallel is off and files run serially inside themselves.
  • Not handled: the printed document opens a new tab and calls window.print(), which blocks on a native dialog. The print scenarios assert the rendered HTML through the API instead. A true UI version needs context.waitForEvent('page') and a stubbed window.print.
Written, not yet run

Every figure and message here was verified against the running API. The suite itself has been typechecked and parsed but never executed — Playwright's browser was deliberately not installed on the server this was written on, which is a live production box. Expect the first local run to need selector adjustments where a label differs from what the markup suggested, and treat that first run as part of the work rather than a regression.
